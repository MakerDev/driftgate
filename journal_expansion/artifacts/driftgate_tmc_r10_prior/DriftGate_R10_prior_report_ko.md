## 1. 판정

**판정은 "닫음"이다.** oracle r를 써도 Δ가 2.0 pp에 미치지 못했다. 판정 값은 `decision.json`에 있다.

- Δ는 후반 구간(평가 라운드 30–150)의 seed 평균으로 계산했다.
  - Δ = max(M1, M2) − max(B0, B1, B2, B3)
  - pp는 정확도 백분율의 차이다.
- 방법(인과 추정 r̂)
  - M1이 64.10%로 M2보다 높다.
  - 가장 좋은 기준은 B3(두 exit의 확률 평균, 65.86%)다.
  - 따라서 Δ = **−1.76 pp**다. M1은 전체 구간에서도 B3보다 낮다(64.14% 대 66.66%).
- oracle r
  - oracle r는 클라이언트가 그 평가 라운드에 받은 요청 가운데 Main 아닌 요청의 실제 비율이다.
  - 이 값을 쓴 M1은 67.52%이고, Δ = **+1.67 pp**로 2.0 pp에 못 미친다.

판정에 쓴 정의는 다음과 같다.
- **M1**: 사전 확률을 보정한 server exit의 argmax다.
- **M2**: 보정한 server exit가 "학습 class(M_k) 안인지"를 정하고, M_k 안에서는 client exit가 class를 정한다.
- **사전 확률 보정**: server exit의 확률에 기기가 지금 받는 요청 구성(Main 아닌 요청의 비율 r)을 사전 확률로 다시 곱하는 방법이다.
- **r̂**: 같은 평가 라운드에서 앞서 도착한 요청만으로 EM을 돌려 구한 r다. EM은 숨은 변수가 있을 때 기댓값 계산과 최대화를 번갈아 하는 추정법이다.

## 5. 이득과 손실이 생긴 곳 (후반 구간, 표 1)

- **M1과 가장 좋은 기준 B3의 차이**
  - 집에서는 M1이 3.0 pp 높고(78.52% 대 75.49%), Main 요청에서도 4.9 pp 높다(87.55% 대 82.63%).
  - 밖에서는 5.3 pp 낮다(51.44% 대 56.69%). Main 아닌 요청에서 크게 낮다: OOP 14.43% 대 35.45%, OOR 6.30% 대 16.74%.
- **r̂가 실제보다 작게 추정된다.** 밖에서는 0.23 대 0.51, 집에서는 0.06 대 0.11이다(표 3). 그래서 보정이 답을 학습 class 쪽으로 지나치게 당기고, Main 아닌 요청을 놓친다.
- **oracle r를 쓴 M1**
  - 밖의 정확도가 B3와 같은 수준(56.58% 대 56.69%)으로 돌아온다. 집과 Main 요청에서는 B3보다 각각 4.8 pp, 4.9 pp 높다.
  - 그래도 OOP(23.11%)와 OOR(10.86%)에서는 B3보다 낮다. 그래서 Δ가 +1.67 pp에 머문다.
- **묶음 추정과 고정 r**
  - 묶음 추정은 인과 추정과 거의 같다(M1 64.12% 대 64.10%).
  - 모두가 집에 있던 시점의 구성을 계속 쓰는 고정 r는 밖에서 더 낮다(48.30%).
- **기본 시스템과의 비교**: 지금 원고의 B0과 비교하면 M1은 후반 구간에서 0.41 pp 높다. 하지만 두 exit의 확률을 평균하는 B3가 B0보다 2.17 pp 높다(후반, 전체 구간에서는 4.12 pp).

## 8. 불일치 기록과 구현에서 정한 것

모두 결과를 보기 전에 정했다.

1. **도착 순서**
   - 평가 요청은 class 순서(Main, OOP, OOR)로 이어 붙여 만들어진다. 그래서 코드가 평가하는 순서를 그대로 쓰면 Main 요청이 모두 먼저 도착하는 셈이 된다.
   - 클라이언트와 평가 라운드마다 무작위 도착 순서를 뽑아 기록했다(`req_arrival`). 난수는 `numpy default_rng([partition seed, 10, round, client])`이고 학습 난수와 무관하다.
   - 인과 추정은 이 순서로 했다. 코드가 평가한 순서도 `req_order`로 남겼다.
2. **π_tr의 라운드**: 평가는 같은 라운드의 학습 직후에 한다. 그래서 "평가 라운드 직전 학습 라운드"를 그 라운드의 학습으로 보고, 그 라운드의 label 개수를 썼다.
3. **label 개수**
   - cell z의 개수는, 그 라운드 학습에서 z에 속해 참여한 클라이언트들의 학습 label 개수를 local epoch 수만큼 곱해 더한 값이다. 두 cell에 속한 클라이언트는 batch마다 두 cell의 server block을 모두 학습하므로 두 cell에 모두 더했다.
   - 전체 개수는 참여한 클라이언트마다 한 번씩 더했다.
   - 학습 표본이 없는 cell은 없었다.
4. **EM의 시작값과 자르기**
   - 요청 전체로 돌리는 EM(r̂_prev, 묶음 추정, 고정 r)은 그 라운드의 r̂_prev에서 시작했다. r̂_prev는 같은 클라이언트의 직전 평가 라운드 요청 전체로 구한 추정값이다.
   - 그래서 평가 라운드 t의 묶음 추정은 라운드 t + 1의 r̂_prev와 같다.
   - EM의 결과는 모두 [0.02, 0.98]로 잘랐다. oracle r도 같은 범위로 잘랐다.
5. **확률의 정밀도**
   - B3, M1, M2는 기록된 float16 확률로 계산했다.
   - B0, B1, B2는 기록된 예측과 entropy(float32)로 계산했다.
   - float16 확률의 argmax는 기록된 예측과 99.99% 같다. 나머지는 반올림으로 생긴 동률이다.
6. **소속 cell**: 평가 라운드의 소속 cell은 `--record_device_signals`가 남기는 기록을 그대로 썼다.
7. **GPU 공유**: run이 도는 동안 다른 프로젝트의 프로세스가 GPU 0–2를 함께 썼다. 결과에는 영향이 없고, 실행 시간만 길어졌을 수 있다.
