- 작성: 2026-10-02, 서버 `honeynaps`(RTX 4090 4장, GPU 0–3 사용)
- 코드: commit `1b77f6a`(Round 7 flag 추가). 실행 전 코드는 commit `85c3cf1`이다.
- run 원본: `journal_expansion/runs/phaseT7_gate/`
- 표·그림·스크립트: `journal_expansion/artifacts/driftgate_tmc_r7_gate/`
- 모든 수치는 run 원본(JSON과 `_trace.npz`)에서 `scripts/r7_gate_analysis.py`가 계산한 CSV(`tables/`)에서 옮겼다.

이 보고서에서 쓰는 말은 다음과 같다.

- **λ**: 클라이언트가 학습 후 자기 모델과 cell(edge 서버 하나가 맡는 영역) 평균 모델을 섞을 때 자기 모델에 주는 비중이다.
- **λ_k**: 클라이언트 k마다 따로 정하는 λ다.
- **Λ**: cell 평균과 전체 평균을 섞을 때 cell 평균에 주는 비중이다.
- **pp**: 정확도 백분율의 차이다.
- **integrated accuracy**: 평가 라운드 31개(1, 5, 10, …, 150)에서 잰 정확도의 평균이다.
- **같은 seed 차이**: 두 arm의 값을 같은 seed끼리 뺀 것이다. [ ]는 Student-t 95% 신뢰구간(CI)이고, (a/3)은 앞 arm이 더 높았던 seed 수다.

## 1. 판정 결과와 핵심 수치

**판정: 규칙 1에 해당한다. 기기 단위 λ로 얻을 수 있는 여지가 작으므로 결과만 보고한다.**

- 규칙 1의 기준은 oracle과 고정 λ의 평균 차이(O − F)가 1.0 pp 이상인지다.
  - oracle(O)은 집에서 λ_k = 0.70, 밖에서 0.15를 쓰는 기준선이다.
  - 측정값은 +0.93 pp [−0.67, +2.53] (3/3)로, 1.0 pp에 못 미친다.
- 규칙 2와 3(D-TV, D-SR의 통과 여부와 신호 선택)은 적용하지 않았다.
  - 참고로 두 기기 단위 arm은 모두 평균이 F보다 낮다.
  - 규칙 2의 기준인 0.5 × (O − F) = +0.46 pp에도 미치지 못한다.
- 규칙 4에 따라 C-Λ − C는 수치만 적는다. 값은 +0.28 pp [−0.35, +0.91] (3/3)이다.
- 판정 결과는 `decision.json`에 있다.

arm은 다음 여섯 개다. S1(출퇴근 이동, 클라이언트 50명, cell 5개)만 썼고 seed는 5, 6, 7이다.

| arm | 내용 |
|---|---|
| F | 고정 λ = 0.4, Λ = 0.5 |
| C | 현재 DriftGate. cell마다 λ와 Λ를 정한다(`--no_neighbor_avg`). |
| C-Λ | C와 같고 Λ만 0.5로 고정한다. |
| D-TV | 기기 단위 λ_k. 클라이언트 자신의 x_TV로 정하고 Λ = 0.5다. |
| D-SR | 기기 단위 λ_k. 클라이언트 자신의 x_SR로 정하고 Λ = 0.5다. |
| O | oracle. 집에서 λ_k = 0.70, 밖에서 0.15를 쓰고 Λ = 0.5다. |

신호의 정의는 다음과 같다.

- **x_TV**: probe 요청에 대해 client exit와 server exit가 낸 확률 벡터의 거리(TV, total variation)의 평균이다.
- **x_SR**: probe 요청 가운데 server exit의 예측 class가 클라이언트의 Main class(학습에 쓴 class) 밖인 비율이다.
- 둘 다 probe의 라벨을 쓰지 않는다.

1. **oracle의 이득은 집에서 나온다.**
   - O는 F보다 집에서 +3.70 pp 높고, 밖에서는 −1.75 pp 낮다(0/3).
   - 밖에서 λ_k를 0.15로 낮춘 결과, 밖의 정확도는 λ 0.4일 때보다 낮았다.
2. **O − F의 40%는 처음 25 라운드(05:00–07:30)에서 나온다.**
   - 이 구간의 기여는 +0.37 pp다(표 2.7).
   - 기기 단위 controller는 이 구간에 warm-up 규칙으로 λ_k = 0.425를 쓴다. oracle은 첫 라운드부터 0.70과 0.15를 쓴다.
   - 라운드 26 이후 구간에서 O − F의 기여 합계는 +0.56 pp다.
3. **두 신호는 집과 밖을 잘 가려내지만, λ_k의 차이는 oracle보다 훨씬 작다.**
   - 집과 밖의 λ_k 차이는 D-SR 0.20, D-TV 0.10이고, oracle은 0.55다.
   - D-TV의 집 λ_k(0.388)는 고정값 0.4보다도 낮다.
4. **C − F(−0.63 pp, 1/3)는 Round 6의 S1 결과와 같은 방향이다.**
   - Round 6 S1(seed 0–4)에서는 −0.59 pp (0/5)였다.
   - seed가 다르므로 두 값을 서로 빼지는 않았다.

### 2.7 보조 분석: 차이를 시간대별로 나눈 값 (`tables/T7_slot_decomposition.csv`)

이 표는 판정에 쓰지 않았다. integrated 차이가 어느 시간대에서 생기는지 보려고 Round 6의 T4b와 같은 방식으로 계산했다.

- 시간대의 기여 = (그 시간대 평가 라운드에서 같은 seed 차이의 평균) × (그 시간대의 평가 라운드 수 / 31)
- 기여를 모두 더하면 integrated 차이가 된다.
- 단위는 pp이다.

괄호 안은 시간대의 평가 라운드 수다. 출근 전 구간에서 O − F의 시간대 평균 차이는 +1.91 pp이고, 세 seed 모두 양수다(+1.55, +2.68, +1.51).

### 4.4 불일치 기록과 구현에서 정한 것

1. **warm-up을 세는 단위**
   - 지시문은 "처음 25 라운드 동안 λ_k = 0.425"라고 했다.
   - 구현은 클라이언트별 관측 횟수가 25 이하인 동안 0.425를 쓴다.
   - S1에서는 모든 클라이언트가 매 라운드 신호를 냈다(18개 run 모두 x_TV, x_SR이 빠진 칸 없음). 그래서 두 정의는 같은 결과를 낸다. 기기 단위 run 6개 모두 라운드 1–25에 λ_k = 0.425였다.
2. **spatial 점수의 기준 값이 3개 미만일 때**
   - 이때는 temporal 점수만 쓰고, spatial EMA 상태는 바꾸지 않고 둔다.
   - 라운드 26–150에서 이런 경우는 클라이언트-라운드의 0.34%(18,750개 가운데 64개)였다.
3. **spatial 기준 집합**
   - 기준 집합은 그 라운드에 클라이언트가 속한 cell(두 개면 합집합)의 구성원 가운데 신호를 보낸 클라이언트들이다. 클라이언트 자신도 포함한다.
   - median과 MAD로 만드는 점수는 cell 단위 controller의 `spatial_z`와 같은 식이다.
     - σ = max(1.4826·MAD, max(10⁻³, 0.10·max(|median|, 0.05)))
     - 점수는 [−2, 6]으로 자른다.
   - S1에는 신호 손실이 없어서 edge와 주고받는 8 byte 메시지는 따로 모의하지 않았다.
4. **두 cell에 속한 클라이언트의 x_SR**
   - server exit의 예측은 두 cell의 server block logit을 평균한 뒤 구한다.
   - 이것은 기존 `probe_forward`의 동작이며, x_TV도 같은 방식이다.
   - 이런 클라이언트-라운드는 seed에 따라 12.8–19.0%다.
5. **oracle의 at_home**: 라운드 시작 시점의 환경 값을 쓴다. 정확도 평가의 집/밖 구분도 같은 값을 쓴다.
6. **arm 명령줄**
   - O에는 `--fixed_Lambda 0.5`와 함께 `--big_lambda_val 0.5`도 넣었다. 두 값은 같다.
   - F는 지시문대로 `--big_lambda_val 0.5`로 Λ를 정했다.
7. **cell λ 기록**
   - 기기 단위 arm과 O의 JSON `lamdas`(cell별 λ)에는 그 cell 구성원의 λ_k 평균을 적었다.
   - 이 값은 기록용이고 학습에는 쓰지 않는다. 학습에 쓴 값은 trace의 `client_lam`이다.
8. **probe 요청**
   - probe 요청은 환경(구성원, ρ, Main class)과 probe 난수만으로 정해진다. 그래서 여섯 arm이 같은 seed에서 같은 probe 요청을 쓴다.
   - probe 풀과 평가 풀은 겹치지 않는다. 18개 run 모두 overlap = 0이다.
9. **추가한 표**
   - 지시문 5.1에 없는 표와 열을 판정과 무관한 보조 자료로 더했다.
     - T3의 C와 C-Λ 행
     - T5의 '이미 넘음' 열
     - T7(시간대별 분해)
     - T8(시간대별 밖에 있는 클라이언트 수)
   - 판정 규칙과 arm, seed는 바꾸지 않았다.
10. **테스트 run의 provenance 기록**
    - 4.3의 테스트 run 8개도 `journal_expansion/provenance/`에 기록이 남았다. 2 라운드 확인 4개와 30 라운드 확인 4개다.
    - provenance는 기록이므로 지우지 않았다. 목록은 `precheck/test_run_provenance.csv`에 있다.
    - 2 라운드 확인 run의 기록에는 commit `85c3cf1`이 적혀 있다. 변경을 commit하기 전에 돌렸기 때문이다.
    - 옛 코드로 돈 run의 기록은 임시 worktree에 쓰였고, worktree와 함께 지워졌다.
11. **실행 환경**
    - 18개 run을 GPU 0–3에 번갈아 배정해 동시에 돌렸다. GPU 0과 1에 5개, GPU 2와 3에 4개다.
    - run 하나는 65–84분 걸렸다(2026-10-02 21:09 시작, 22:33 종료).
