## 0. 이 보고서에서 쓰는 말

- **λ_t**: 학습에 쓴 개인화 비율이다. T15는 0.15, T40은 0.4, T60은 0.6이고, Λ는 0.5다.
- **λ_inf**: 추론에만 쓰는 섞는 비율이다. 0.15, 0.3, 0.4, 0.55, 0.7의 다섯 블록이 기록되어 있다. T60에는 설치된 모델(0.6)의 블록도 있다.
- **M_k**: 클라이언트 k의 Main class 목록이다. 클라이언트 자신의 학습 데이터에서 오므로 규칙에 쓸 수 있다.
- **τ와 entropy routing**: client exit의 entropy가 τ 이하이면 client exit의 예측을 답으로 쓰고, 넘으면 server exit의 예측을 쓴다. τ는 0부터 2.30까지 0.05 간격으로 두었다. 여기에 "client exit만"(τ = 무한대)과 "server exit만"을 더했다.
- **정확도**: 평가 라운드마다 클라이언트 정확도를 같은 비중으로 평균한 뒤 평가 라운드에서 평균한 값이다.
- **두 구간**
  - 후반 구간: 평가 라운드 30–150(25개)이다. 판정은 이 구간으로 했다.
  - 전체 구간: 평가 라운드 31개 전부다.
- **server 사용 비율**: server exit의 예측을 답으로 쓴 요청의 비율이다. 요청 수로 가중한다.
- **pp**: 정확도 백분율의 차이다.
- **[ ]와 (a/3)**: [ ]는 Student-t 95% 신뢰구간이고, (a/3)은 값이 양수인 seed 수다.
- **두 배치**
  - 배치 A: 기기에 server block 사본이 있어, 모든 요청에서 두 exit를 다 계산할 수 있다.
  - 배치 B: server block이 edge에만 있어, server로 보낸 요청에서만 server exit의 출력을 얻는다.
- **규칙**
  - A-고정: entropy routing이다.
  - A-범위: server 예측이 M_k 밖이면 server 예측을, 아니면 client 예측을 쓴다.
  - A-범위-τ: server 예측이 M_k 밖이고 entropy가 τ를 넘을 때만 server 예측을 쓴다.
  - A-두 블록: client 예측은 블록 a에서, server 예측은 블록 b에서 가져와 A-범위를 적용한다.
  - A-종류 oracle: 정답 종류가 Main이면 client 예측을, 아니면 server 예측을 쓴다.
  - B-고정: Round 8의 B\*와 같고, λ_inf도 고를 수 있다.
  - B-범위: client 예측이 M_k 밖이거나 entropy가 τ를 넘으면 server로 보낸다.
  - B-종류 oracle: Main 아닌 요청만 server로 보낸다.

**결과를 읽을 때 함께 볼 값**

1. **A-범위는 Main 요청을 망친다.**
   - A-범위에서 Main 요청의 20.2%가 server로 넘어갔다(후반 구간, 가장 좋은 설정).
   - 이렇게 넘어간 Main 요청의 답은 반드시 틀린다. server 예측이 M_k 밖인데 정답은 M_k 안에 있기 때문이다.
   - 그래서 Main 정확도가 A-종류 oracle의 88.3%에서 72.4%로 내려간다.
   - Main 아닌 요청의 27.0%는 client exit에 남는다.
2. **기기에서 얻는 세 신호는 요청 종류를 잘 가려내지 못한다** (5절, 판정 뒤에 추가한 표).
   - server 예측이 M_k 밖인 비율: Main 아닌 요청의 48–79%, Main 요청의 13–26%
   - client 예측이 M_k 밖인 비율: λ_inf 0.4 이상에서 Main 아닌 요청의 17% 이하. 개인화된 client exit는 거의 언제나 Main class를 예측한다.
   - client exit의 entropy로 Main 아닌 요청을 가려내는 AUROC: 0.63–0.71
3. **배치 B에서는 곡선이 거의 평평하다.** 후반 구간의 B-고정은 server 사용 0.3–1.0에서 64.1–64.7%에 머문다. B-범위는 server 사용 0.3에서만 B-고정보다 0.15–0.72 pp 높다.

### 6.2 불일치 기록과 구현에서 정한 것

1. **M_k의 출처**
   - 지시문대로 분할 코드(`src/r6_requests.build_partition`)로 다시 만들었다. partition seed와 환경 파일은 각 run의 JSON 설정에서 가져왔다.
   - provenance 기록과 같은지 모든 run에서 확인했다.
2. **블록 범위**
   - 블록 하나를 쓰는 규칙(A-고정, A-범위, A-범위-τ, A-종류 oracle, B-고정, B-범위)은 기록된 블록 전부를 후보로 두었다. T60은 설치된 모델(0.6)도 포함된다.
   - 두 블록을 쓰는 규칙(A-두 블록, A-종류 oracle의 쌍)은 지시문대로 λ_inf 격자의 25쌍만 계산했다.
3. **τ 격자의 끝**
   - A-고정과 B-고정에는 τ 격자, τ = 무한대(client exit만), "server exit만"을 모두 넣었다.
   - τ = 0과 "server exit만"은 entropy가 정확히 0인 요청에서만 다르다. 후반 구간의 가장 좋은 A-고정이 τ = 0으로 기록된 것은, 두 설정의 값이 같을 때 앞의 것을 고르기 때문이다.
4. **B-범위의 끝점**
   - τ = 무한대에서는 "client 예측이 M_k 밖"인 요청만 보낸다.
   - "모두 보냄"도 곡선의 한 점으로 넣었다.
5. **곡선 보간**: B-고정과 B-범위의 곡선은 Round 8과 같이 이웃한 두 τ 사이를 선형 보간했다. 그 지점에서 나눈 정확도도 같은 비중으로 보간했다.
6. **최댓값을 고르는 방법**
   - G_A는 지시문대로 설정을 seed 평균으로 고른 뒤 seed별 차이를 냈다.
   - G_B는 "seed마다 계산한다"는 문장에 따라 seed마다 비교 지점별 최댓값을 썼다. Round 8의 B\*와 같은 방법이다.
7. **B-종류 oracle**: 답을 정하는 방법이 A-종류 oracle(블록 하나)과 같아 정확도도 같다. 배치 B에서는 server 사용 비율이 Main 아닌 요청의 비율이 된다(후반 38.1%, 전체 34.5%).
8. **잘못 고른 비율**: 요청 수로 가중해 계산했다. 정확도는 클라이언트를 같은 비중으로 평균한다.
9. **5절의 보조 표**: 결과를 본 뒤 추가했고, 판정에 쓰지 않았다.
10. **새 run과 산출물**: 새 run은 돌리지 않았다. Round 8 산출물도 수정하지 않았다.
