## 0. 이 보고서에서 쓰는 말

- **B0**: entropy routing이다. client exit의 entropy가 0.8 nats 이하이면 client exit의 답을, 넘으면 server exit의 답을 쓴다. 지금 원고의 추론 방식이다.
- **B1, B2**: B1은 client exit만, B2는 server exit만 쓴다.
- **B3**: 두 exit의 확률을 평균해 가장 큰 class를 답으로 쓴다.
- **F (결합)**: 답은 argmax [0.2·p_c + 0.8·p'_s]다.
  - p_c는 client exit의 확률이다.
  - p'_s는 server exit의 확률에서 cell의 학습 분포가 만든 치우침을 지운 확률이다(보정 세기 r = 0.5).
- **종류 oracle**: 정답 요청 종류를 알고, Main 요청에는 client exit, 나머지 요청에는 server exit의 답을 쓰는 참고 규칙이다.
- **요청 종류**
  - Main: 클라이언트가 학습한 class의 요청
  - OOP: 지금 cell의 다른 클라이언트만 학습한 class의 요청
  - OOR: 그 밖의 class의 요청
- **λ 조절**: DriftGate가 TV 신호로 cell마다 학습 λ를 바꾸는 방법이다. "고정 λ 0.4"는 λ를 0.4로 고정한 학습이다.
- **정확도**: 평가 라운드마다 클라이언트 정확도를 같은 비중으로 평균한 뒤 평가 라운드에서 평균한다.
  - 후반 구간: 학습 라운드 30 이후의 평가 라운드다. 결정은 이 구간으로 한다.
  - 전체 구간: 모든 평가 라운드다.
- **표기**: pp는 정확도 백분율의 차이다. 값은 seed 평균이다.

### 7.2 일치 확인

- **B0 정확도와 기존 run의 정확도(전체 구간)**
  - 50개 가운데 47개는 0.3 pp 이내로 같다.
  - 0.3 pp를 넘은 run은 ResNet-18의 세 개다: `r12_e2_res_fx40_A_s0` +0.33, `r12_r0_e2_res_relonly_A_s0` −0.96, `r12_r0_e2_res_relonly_A_s1` −0.33 pp.
  - 이 세 run도 다시 계산한 값은 이번 run의 JSON과 정확히 같다. 그래서 기록 문제가 아니며, 같은 설정을 다시 학습할 때 생기는 run 사이의 차이로 본다.
  - 근거
    - Round 5 경로의 학습 코드는 기준 run 이후 바뀌지 않았다. 바뀐 것은 `signals/library.py`의 기본값이 꺼진 옵션 하나뿐이다.
    - GPU 학습은 bit 단위로 재현되지 않는다. 세 run 모두 첫 라운드부터 평균 손실이 1e-4 ~ 6e-4만큼 다르고, 그 차이가 학습 중에 커진다. 최대 차이는 ResNet-18에서 0.015로, 작은 CNN(단계적 구성 변화 seed 0, 0.002)의 7배다.
    - DriftGate run은 λ 조절이 시작되는 라운드 25부터 seed 0–2 모두 λ가 달라진다. 이후 125개 라운드에서 λ가 다르다.
  - 기준 run이 돈 서버는 다르다. `e2_res_fx40_A_s*`는 옛 서버에서, `r0_e2_res_relonly_A_s*`는 이 서버에서 돌았다.
- **기록 확인**
  - Round 5 경로 run의 요청별 기록에서 다시 계산한 정확도는 평가 함수와 모든 클라이언트-라운드에서 같았다(불일치 0건).

### 7.3 불일치 기록과 구현에서 정한 것

1. **K = 500의 클라이언트 번호 (결과를 본 뒤 고침)**
   - Round 6 runner는 요청별 클라이언트 번호를 `uint8`로 저장했다. 그래서 K = 500에서 256 이상의 번호가 0부터 다시 시작했다.
   - 처음 분석에서 K = 500의 B0 재계산이 JSON과 0.44–0.60 pp 달라 이 문제를 찾았다.
   - 기록은 평가 라운드마다 클라이언트 번호 순서로, 클라이언트마다 `eval_n_total`개씩 이어져 있다. 분석 스크립트는 이 순서로 번호를 되살린다.
     - 되살린 번호를 256으로 나눈 나머지가 저장된 번호와 같은지 확인한다.
     - 평가 라운드 번호가 맞는지 확인한다.
   - 고친 뒤 K = 500의 B0 재계산은 JSON과 0.01 pp 이내로 같다.
   - 이 수정으로 K = 500의 F − B0는 +1.02 pp(잘못 읽은 값)에서 +0.81 pp로 바뀌었고, 결정 1의 답은 그대로다. 다른 run은 영향을 받지 않는다.
   - runner의 저장 형식은 `int16`으로 고쳤다(이번 run과 무관한 이후 기록용).
2. **Round 5 경로의 기록**
   - `src/runner.py`와 `scripts/run_v2.py`에 flag 세 개를 넣었다: `--record_eval_probs`, `--record_train_label_hist`, `--record_device_signals`. Round 5 경로에서 `--record_device_signals`는 평가 라운드의 소속 cell을 기록한다.
   - 확률은 test 데이터를 tensor로 한 번 만들어 둔 뒤 기록했다. 원래 평가 함수의 DataLoader는 전역 난수를 소비하기 때문이다.
   - 이 시나리오들에는 집 개념이 없어 at_home은 비워 두었다.
   - 평가 라운드는 원래대로 10 라운드마다이고, 후반 구간은 라운드 30 이후다. 그래서 단계적 구성 변화, ResNet-18, CIFAR-100은 평가 라운드 13개, client mobility는 10개다.
3. **M_k**: 각 클라이언트의 Main 요청 label을 모아 만들었다. 모든 요청에서 "label이 M_k 안"과 "종류가 Main"이 일치하는지 확인했다.
4. **π_tr**: 평가 라운드와 같은 라운드의 학습 label 개수와, 평가 라운드의 소속 cell로 만들었다. π_tr는 server exit가 학습할 때의 사전 확률이다.
5. **기존 명령줄**
   - 각 run은 기존 run의 provenance 명령줄을 그대로 쓰고, 이름, 출력 위치, 기록 flag만 바꿨다.
   - 옛 서버 경로는 현재 저장소 경로로 바꿨다.
   - `s1_driftgate_own_s*`의 `--save_models`도 그대로 두었다.
6. **결정 1의 run**: 고정 λ 0.4 run으로 판정했다. DriftGate run의 F − B0는 표 1에 함께 적었다.
7. **실행**
   - 실행 관리자(`scripts/r12_dispatch.py`)가 GPU 메모리 여유를 보고 우선순위 순서로 띄웠다. 순서는 S1, 단계적 구성 변화, client mobility, 그다음 나머지다.
   - 50개 모두 첫 시도에 끝났다.
   - 다른 프로젝트의 학습 프로세스가 같은 GPU를 함께 썼다.
