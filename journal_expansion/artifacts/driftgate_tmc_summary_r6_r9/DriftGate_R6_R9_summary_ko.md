## 0. 결론 요약

1. **상황에 따라 학습 λ를 바꾸는 방법은 이동 시나리오에서 잘 고른 고정 λ를 넘지 못했다.**
   - cell 단위 DriftGate(Round 6)와 기기 단위 λ(Round 7) 모두 그렇다.
   - 기존 원고의 대표 결과(Round 5 설정, 단계적 구성 변화와 client mobility)는 이웃 평균을 뺀 최종 정의에서도 유지된다.
2. **클라이언트가 집에 있는지 밖에 있는지는 기기 신호로 잘 가려진다.** λ 0.4로 학습한 모델에서 x_SR의 AUROC는 0.96, x_TV는 0.90이다. 하지만 그 판단을 정확도 이득으로 바꾸는 데서 막혔다.
   - 학습 λ를 바꾸면 개인화의 이득과 공유의 이득이 서로 깎인다(Round 7).
   - 추론에서만 쓰면 미리 정한 판정은 통과한다(Round 8). 그러나 이득의 절반 이상은 집과 밖을 구분해서 생긴 것이 아니다. probe 비용을 넣으면 이득이 크게 줄어든다.
3. **가장 큰 여지는 요청마다 어느 exit의 답을 쓸지 정하는 데 있다.**
   - 요청 종류(학습한 class인지)를 정답으로 아는 oracle은 지금의 entropy routing보다 약 9 pp 높다.
   - 그러나 기기에서 얻는 정보(예측 class가 학습 class 안인지, entropy)로 만든 규칙은 이득을 내지 못했다(Round 9).
4. **지금의 entropy routing(τ = 0.8)은 효율이 낮다.** 평가 라운드 전체 평균으로는, server를 전혀 쓰지 않는 쪽(63.67%)이 server를 90% 쓰는 τ = 0.8(62.54%)보다 높다.

## 1. 용어

- **λ**: 클라이언트가 학습 뒤 자기 client block과 cell 평균을 섞을 때 자기 쪽에 주는 비중이다.
  - λ_t는 학습에 쓰는 값, λ_inf는 추론에만 쓰는 값이다.
  - Λ는 cell 평균과 전체 평균을 섞는 비중이다.
- **DriftGate**: cell(edge 하나가 맡는 영역)마다 TV 신호로 λ와 Λ를 정하는 controller다. 2026-10-01부터 이웃 cell과 점수를 평균하는 단계를 뺀 정의를 최종으로 쓴다.
- **신호**
  - TV(x_TV): 같은 요청에 대해 client exit와 server exit의 확률 벡터가 다른 정도다.
  - x_SR: server exit의 예측이 클라이언트의 Main class 밖인 비율이다.
  - Main class: 클라이언트가 학습한 class다.
- **요청 종류**: Main은 학습한 class다. OOP는 지금 cell의 class 가운데 학습하지 않은 것이고, OOR은 그 밖의 class다.
- **τ와 entropy routing**: client exit의 entropy가 τ 이하이면 client exit의 답을, 넘으면 server exit의 답을 쓴다. 지금까지 기본값은 0.8이었다.
- **server 사용 비율**: server exit의 답을 쓴 요청의 비율이다.
- **시나리오**: S1은 출퇴근 이동이다(클라이언트 50명, cell 5개, 150 라운드, 05:00–20:00). S2는 GeoLife 실제 궤적이다.
- **표기**
  - pp는 정확도 백분율의 차이다.
  - 차이는 같은 seed끼리 뺀 값이다. [ ]는 95% 신뢰구간이고, (a/n)은 앞의 방법이 높았던 seed 수다.

6. **T40, τ = 0.8**: 정확도 62.54%이고 server 사용은 89.9%다. 같은 모델로 client exit만 쓰면 63.67%다. 정답을 아는 routing 상한은 약 75%다.

### 2.5 Round 9: 요청마다 학습 class 기준으로 exit 고르기 (새 run 없음)

- **배치 A**: 기기에 server block 사본이 있다. 규칙은 "server 예측이 학습 class 밖이면 server, 아니면 client"다.
- **배치 B**: server block은 edge에만 있다. 규칙은 "client 예측이 학습 class 밖이거나 entropy가 τ를 넘으면 server로 보냄"이다.
- 판정은 평가 라운드 30–150으로 했다.

| 값 | 평가 라운드 30–150 | 전체 31개 라운드 |
|---|---|---|
| 배치 A: 범위 규칙 − 가장 좋은 고정 τ | −1.40 pp [−1.69, −1.11] (0/3), 기준 3.0 | −2.93 pp |
| 배치 B: 범위 규칙 − 고정 τ (server 사용 0.3, 0.5, 0.7) | +0.14 pp [−0.16, +0.44] (3/3), 기준 2.0 | +0.24 pp |
| 종류 oracle − 가장 좋은 고정 τ (배치 A) | +8.91 pp (73.52% 대 64.61%) | +8.88 pp |
| 종류 oracle − 같은 server 사용의 고정 τ (배치 B, server 사용 38.1%) | +9.12 pp | +10.13 pp |

범위 규칙이 실패한 이유는 다음과 같다.

- **server 예측으로 가려내기**: server 예측이 학습 class 밖인지로 보면 Main 아닌 요청의 48–79%를 표시한다. 그러면서 Main 요청도 13–26% 표시한다. 이렇게 server로 넘어간 Main 요청의 답은 반드시 틀린다.
- **client 예측으로 가려내기**: 개인화된 client exit는 Main 아닌 요청에도 거의 언제나 학습 class를 예측한다. λ_inf 0.4 이상에서 학습 class 밖 예측은 Main 아닌 요청의 17% 이하다.
- **entropy로 가려내기**: client exit의 entropy로 Main 아닌 요청을 가려내는 AUROC는 0.63–0.71이다.

## 3. 라운드를 가로질러 보이는 사실

1. **학습 λ를 상황에 따라 바꾸는 접근**
   - 이동 시나리오(S1, S2, S1-fast, K = 200/500, 견고성 조건)에서는 cell 단위와 기기 단위 모두 고정 λ를 넘지 못했다.
   - 고정 λ끼리의 차이도 작다. 가장 좋은 값과 두 번째 값의 차이는 대부분 0.5 pp 미만이다.
   - Round 5 설정(단계적 구성 변화, client mobility)에서는 DriftGate가 고정 λ, entropy controller, absonly보다 높다.
2. **신호의 성격**: 신호는 "클라이언트가 지금 학습 분포 밖에 있는지"를 잘 가려낸다(λ 0.4로 학습한 모델에서 클라이언트 단위 AUROC 0.90–0.96. λ 0.15에서는 x_TV가 0.71로 낮다). 그러나 "이 요청이 학습 class인지"는 잘 가려내지 못한다(요청 단위 AUROC 0.63–0.71, 학습 class 밖 예측의 오표시).
3. **이득의 위치**: 요청 종류를 아는 routing은 약 9 pp 높다. 반면 λ를 상황에 맞추는 방법들의 oracle은 0.9–3.1 pp에 그친다. 정확도의 여지는 λ보다 routing에 훨씬 크다.
4. **학습 초반의 영향**
   - 처음 25 라운드에는 server exit가 아직 약해 server를 쓰면 정확도가 크게 떨어진다. T40 seed 5의 평가 라운드 1에서는 client exit만 쓰면 63%, τ = 0.8이면 36%다.
   - 이 구간이 Round 7의 oracle 이득과 Round 8의 신호 정책 이득에 큰 몫을 차지한다.
   - 평가 라운드 30 이후에는 server exit만 쓰는 쪽이 가장 좋은 고정 설정이 된다(Round 9).
5. **비용**: 신호를 매 라운드 64개 probe로 만들면 요청의 69–75%를 server로 보내는 셈이다. probe 비용을 넣으면 Round 8의 신호 정책 이득은 대부분 사라진다.

## 4. 해석할 때 주의할 점

- **시나리오와 seed 수**: Round 7–9는 S1 한 시나리오, seed 3개(5–7)다. Round 6의 S2는 seed 3개이고 seed 사이 표준편차가 3–5 pp로 크다.
- **같은 자료에서 고른 최댓값**: Round 8과 9의 "가장 좋은 설정"은 같은 평가 자료에서 골랐다.
  - τ를 두 개 쓰는 정책은 자유도가 커서 유리하다. 무작위 표지만으로도 G가 약 +1 pp 생기는 것이 그 크기를 보여 준다.
- **판정 뒤에 덧붙인 확인**: Round 8의 시간대 분해, 무작위 표지, 같은 λ_inf 통제와 Round 9의 가려내기 표는 결과를 본 뒤 계산했다. 판정 규칙은 바꾸지 않았다.
- **GPU 재현성**: GPU 학습은 bit 단위로 재현되지 않는다. 같은 명령의 정확도 차이는 0.01–0.03 pp 수준이다.
- **기기 측정**: 지연 시간의 클라이언트 쪽 값은 서버 CPU에서 잰 임시값이다. 실제 기기 측정 준비물은 Round 6의 `device/`에 있다.

## 5. 방향을 정할 때 답해야 할 질문

결과가 직접 답하지 않은 질문을 적는다. 어느 쪽을 택할지는 제안하지 않는다.

1. **원고의 주장 범위**: Round 5 설정(단계적 구성 변화, client mobility)에서 유지되는 DriftGate 결과를, Round 6 이동 시나리오의 반대 결과와 함께 어떻게 담을 것인가.
2. **기여의 중심**: 정확도 여지가 큰 routing을 주제로 삼을 것인가. 그렇다면 요청 단위로 "학습 class인지"를 가려내는 신호가 필요하다. 지금 기록된 신호(entropy, 예측 class)로는 가려지지 않았다.
3. **신호를 쓰는 곳**: 상황 판단(AUROC 0.96)을 정확도가 아닌 다른 목적에 쓸 것인가. 예를 들면 비용이나 server 사용 절감이다. 그때 probe 비용을 어떻게 줄일 것인가(8개면 AUROC 0.86).
4. **기본 routing 설정**: τ = 0.8이 학습 초반과 후반 모두에서 비효율적이라는 결과를 기존 결과의 해석에 어떻게 반영할 것인가.
